# 06 · 模板设计要点

`templates/` 里的文件可以直接抄，但**照抄不改等于没做**。这份文档说明每份模板为什么长这样，以及抄完必须改哪些地方。

---

## 1. 标签体系：五类，不是一类

标签混乱的根因通常是"只按内容打标签"。内容标签无法回答**成熟度**和**用途**。

| 类 | 数量约束 | 回答的问题 | 谁在用 |
|:---|:---|:---|:---|
| **状态** | 必打 1 个 | 这份东西成熟到什么程度？ | 治理（找积压）、复盘 |
| **类型**（内容性质） | 打 1–3 个 | 这是什么性质的内容？ | `/检索` `/灵感` 筛选 |
| **文档类型**（工作阶段） | 必打 1 个 | 属于哪个工作环节？ | **生成器检索过往范例的主键** |
| **领域** | 打 1–3 个 | 讲的是什么主题？ | 跨库关联 |
| **优先级** | 打 1 个 | 值不值得反复回看？ | 精华池确权 |

### 状态流转要有明确建议

| 标签 | 含义 | 流转建议 |
|:---|:---|:---|
| `#待整理` | 刚入库，未消化 | 一周内处理，否则进"待消化积压"预警 |
| `#已消化` | 读过、提炼过要点 | 可进入关联/复用 |
| `#待复盘` | 需结合项目/周期复盘 | 周末 `/复盘` 时优先 |
| `#精华` | 高价值、常回看 | 会被"每日灵感"抽取 |
| `#过期` | 已失效、待清理 | 下次 `/标签` 治理时归档/删除 |

> **没有流转建议的状态标签等于装饰。** 加上"一周内处理"这种量化约束，它才会真的被推动。

### 文档类型标签要和工作阶段一一对应

`#需求收集` `#需求分析` `#方案设计` `#报价` `#立项` `#投标` `#PRD` `#进展汇报` `#配置参考`

这组标签的价值不在"分类"，而在**让"检索同类历史范例"变成一次精确查询**。
所以它的取值集合必须**封闭**（不能随时新增同义词），并且与工作项目库的目录结构对应。

### 自动化触发建议要写进文档

```markdown
- 含 `#PRD` + `#工程AI设计` → 归入 **工作项目库**
- 含文档类型标签 → 归入 工作项目库/<项目名>/ 对应阶段，供生成器检索
- 含 `#精华` → 进入"每日灵感"候选池
- 含 `#待整理` 超过 7 天 → 周报预警
```

> 这一段是**给 Agent 看的规则**。写清楚，Agent 才能自己判断归档到哪。

### 治理规则

- 同义合并（如"竞品"与"竞品分析"）
- 使用次数 < 2 的标签考虑废弃
- 每月扫描一次
- **停用的标签要写停用日期和迁移策略**（"存量保留不迁移，新文档一律用新标签"）

## 2. 全局提示词：为什么必须分五段

| 段 | 作用 | 抄完必须改什么 |
|:---|:---|:---|
| 【角色设定】 | 定职责边界（**不是"回答问题"，是"管理知识"**） | 改成你的行业背景 |
| 【记忆规则】 | 记偏好 / 项目 / 风格 / 阶段目标 | **必须改**，这是最个人化的一段 |
| 【知识库调用原则】 | 优先检索、标注来源、指出矛盾 | 基本不用改 |
| 【成长进化规则】 | 让 Agent 主动发现你的盲区 | 可保留，可减弱 |
| 【输出规范】 | 先结论 → 依据 → 行动 | 按你的偏好改 |

**三条不能删的**（删了这套方法就退化成普通聊天）：
1. 优先检索知识库，找不到再补充通用知识
2. 引用必须标注来源
3. 发现矛盾主动指出并询问以哪个为准

## 3. 库 README：六节结构，重点在第二节

```
定位一句话 → 适合放入 → 不适合放入 → 命名规范 → 必打标签 → 入库方式
```

**为什么"不适合放入"比"适合放入"更重要**：
"适合放入"只描述意图，"不适合放入"才划出边界。
人对边界的记忆比对意图的记忆弱得多 —— 所以必须写下来，并且写**具体反例**。

反例的正确写法：

> ❌ `- 不适合放入：外部资料`
> ✅ `- 教材 / 真题原文 / 题库等外部权威知识的搬运 → 放库外 ..\_参考库\`
>    `  判断标准：这是你产出的，还是别人产出你只是搬运的？`

## 4. 上手清单：为什么按周分，不按功能分

按功能列（"入库 / 检索 / 写作 / 关联..."）看起来完整，但**没人会一次学完**。

按周分，每周只解决一个问题：

| 周 | 目标 |
|:---|:---|
| 第 1 周 | 跑通入库与检索 |
| 第 2 周 | 写与连 |
| 第 3 周 | 项目与复盘 |
| 第 4 周 | 补齐闭环 |

**关键**：每周的验收标准是"**在真实工作上用过一次**"，而不是"知道有这个功能"。
第 2 周的要求写成"用 `/写作` 基于知识库写一份**真实交付物**"，不是"试一下 `/写作`"。

---

## 5. 索引：为什么只留一处

见过很多知识库有 3 个导航文件：`导览.md`、`README.md`、`索引.md`，内容各有一半是旧的。

**规则：导航只有一处。** 其他文件不写目录结构，只写自己领域内的规则。
好处：
- 文件移动时只需要改一个地方
- 不会出现"两处导航互相矛盾"
- 新人（或未来的你）只需要记一个入口

---

## 6. 抄模板的正确姿势

1. 先读一遍所有模板，理解**为什么**这么写
2. 复制到自己的 Vault
3. **把每一个占位符替换掉**（`<项目名>`、`XX考试`、`<你的路径>`）
4. 库 README 的"不适合放入"要写**你自己**最想乱丢的东西
5. 全局提示词的【记忆规则】要从你的真实处境写起，不要抄示例
6. 跑完第一周之后回来**改一次**模板 —— 你会发现第一版一定有不合适的地方

> 模板是起点，不是终点。**能改的模板才是活模板。**
