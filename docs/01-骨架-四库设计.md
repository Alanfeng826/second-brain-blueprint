# 01 · 骨架：四库怎么分，边界怎么定

骨架层是一棵纯 Markdown 目录树。它的唯一目标是：**让"我产出的判断"和"别人产出的原料"不在同一棵树上。**

---

## 1. 为什么是四个库，而不是"按主题分类"

最常见的失败做法是按主题建目录（`产品/`、`技术/`、`行业/`、`考试/`）。
问题在于：**主题会互相穿透，而且无法回答"这份东西的成熟度"**。
一篇行业报告、一份自己的复盘、一个可复用模板，主题可能都是"AI"，但它们在你脑子里的角色完全不同。

四个库是按**角色**分的：

| 库 | 角色 | 回答的问题 | 生命周期 |
|:---|:---|:---|:---|
| **工作项目库** | 正在发生的事 | "这个项目当时是怎么想的？" | 随项目起止，长期留存 |
| **产品洞察库** | 我的思考与外部输入 | "我对这件事的判断是什么？" | 持续累积，可发酵 |
| **学习成长库** | 系统性学习的沉淀 | "我为此学到了什么？" | 随考试/课程周期，可归档 |
| **素材模板库** | 可复用的零件 | "下次直接拿什么来用？" | 长期复用，可版本化 |

四库之外还有两个**库外目录**，它们不参与检索：

| 目录 | 层 | 装什么 | 为什么在库外 |
|:---|:---|:---|:---|
| `_参考库/` | 原料层 | 教材、真题、标准原文、行业报告 | 体量大、非自有产出，混入会稀释信噪比 |
| `归档/` | 历史层 | AI 中间产物、过期文件 | 是过程垃圾，但有回滚价值 |

## 2. 每个库的 README 是"宪法"，六节结构

库说明不是介绍文档，是**约束文档**。六个必写章节：

```markdown
# 📁 <库名>

存放<一句话定位>。这是"<它在知识体系里的角色>"的沉淀地。

## 适合放入
- ...

## 不适合放入   ← 最重要的一节，没有它就一定会膨胀
- ...

## 命名规范
`<规范>`，例：`<示例>`

## 必打标签
- 状态：...
- 类型：...
- 领域：...
- 优先级：...

## 目录结构（可选，库内子目录约定）
| 目录 / 文件 | 放什么 | 参与检索 |
|:---|:---|:---|

## 入库方式
- ...
```

> **"不适合放入"这一节怎么写？**
> 写你现在最想往里丢、但不该丢的东西。
> 例：学习成长库 → "教材 / 真题原文 / 题库等外部权威知识的搬运 → 放库外 `_参考库\`"，
> 并附上判断标准：**"这是你产出的，还是别人产出你只是搬运的？"**

可直接复制的四份库说明在 [`../templates/库README/`](../templates/库README/)。

## 3. 工作项目库的特殊设计：目录即项目，文件名即阶段

其他三个库是平铺的，工作项目库必须**按项目分子目录**，否则不同项目的投标书会互相污染检索结果。

```text
工作项目库/
└── <项目名>/
    ├── 需求收集-<客户>.md    # 文档类型标签 #需求收集
    ├── 需求分析-<客户>.md    # #需求分析
    ├── 方案设计-<客户>.md    # #方案设计
    ├── 报价-<客户>.md        # #报价
    ├── 立项-<项目名>.md      # #立项
    ├── 投标-<项目名>.md      # #投标
    ├── PRD-<版本>.md         # #PRD
    └── 进展-<周期>.md        # #进展汇报
```

这里的**文档类型标签**是整套设计里最巧的一处：它让"生成器检索过往范例"变成一次精确的目录内查询，而不是全库模糊搜索。

> 当你要写一份新的投标文件时，Agent 只需要：定位同类历史范例 → 抽结构 → 套新上下文。
> 这就是 [`../../docs/02-大脑-Agent接入.md`](02-大脑-Agent接入.md) 里"生成型指令"能工作的前提。

额外约定：优质范例在标题下补一个 `#范例` 标签，生成器**优先**套用它。

## 4. `_系统/` 目录：把规则本身也存进知识库

这是整套方法里最容易被忽略、但收益最高的一步：**规则也要版本化**。

| 文件 | 作用 | 谁会读它 |
|:---|:---|:---|
| `索引.md` | 总导航。四库＋库外＋指令表＋自动化清单 | **你**（唯一需要记住的入口） |
| `标签体系.md` | 五类标签标准与治理规则 | **你 + Agent** |
| `全局提示词.md` | Agent 的人设与调用原则 | **Agent** |
| `上手清单.md` | 分阶段落地路线 | **你** |

为什么必须放进 Vault 而不是记在脑子里：
1. **可迁移** —— 换机器、换 Agent，规则跟着 Vault 走
2. **可迭代** —— 标签体系改版有 diff 可查
3. **可交付** —— 这套方法能打包给别人，就是因为规则是文件

## 5. `索引.md` 应该长什么样

它是唯一入口，所以要回答三件事：**东西在哪、能下什么指令、有什么在自动跑。**

```markdown
# 🗂️ 个人知识库索引

> 知识库根目录：`<你的路径>`
> 四库：工作项目库 / 产品洞察库 / 学习成长库 / 素材模板库
> 系统文档：`_系统\`（本目录）

## 一、知识库导航

**四库 —— 观点层（你产出的知识，参与检索 / 灵感 / 关联）**
| 库 | 内容 | 说明文件 |
|:---|:---|:---|

**库外 —— 原料层 / 历史层（默认不参与语义检索）**
| 目录 | 内容 | 说明文件 |
|:---|:---|:---|

## 二、内置指令
| 指令 | 作用 | 绑定库 |
|:---|:---|:---|

## 三、自动化任务
- 每周知识复盘：...
- 每日灵感推送：...

## 四、系统文档
- `_系统/标签体系.md`：...
```

完整版见 [`../templates/_系统/索引.md`](../templates/_系统/索引.md)。

## 6. 建库检查清单

- [ ] 四个库目录已建（空目录就够，不要急着丢文件）
- [ ] `_系统/` 四份文档已就位，且**已改成本人背景**（模板里的占位符全部替换）
- [ ] 四份库 README 已写，且每份都有"不适合放入"章节
- [ ] 工作项目库的文档类型标签清单已确定（这是生成器的检索主键）
- [ ] `索引.md` 能在一屏内说明"东西在哪、能做什么"
- [ ] 决定 `_参考库` 的初始主题（没有就留空目录，用起来再建）

> ⚠️ 不要一上来就迁移历史文件。**先让新东西按新规则进来，旧文件在第一次治理时再分批搬。**
> 一次性大迁移会让你在没有验证规则的情况下，把错误的规则应用到全部历史数据上。
